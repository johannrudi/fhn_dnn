# Split `data` params into `data_train` / `data_evaluate`

## Context

`pytorch/configs/params_dnn.yaml`'s `data:` block mixes truly shared settings (data directory, normalization flags, memmap column counts) with settings that conceptually belong to either the training split (`Ntrain`, `Nvalidate`, `train_shuffle_buffer_size`, `train_batch_size`) or the evaluation split (`Ntest`, `eval_batch_size`), plus a group of feature/target preprocessing knobs (`features_type`, `features_use_channels_range`, `features_sub_length`, `features_sub_begin_random`, `features_sub_begin_sequence`, `features_sub_step`, `features_additive_noise_std`, `targets_type`) that the user wants duplicated into both new blocks so they can eventually diverge between train and eval.

The target shape, exactly as given by the user, is:

- `data:` keeps `data_dir`, `file_names`, `features_normalize`, `targets_normalize`, `features_use_length_range`, `features_cols_num`, `targets_cols_num`, `features_noise_cols_num`, `targets_noise_cols_num`, `features_fft`, `num_features` (derived), `num_targets` (derived), `autoencoder_load_dir`, `autoencoder_latent_size` — i.e. every key not explicitly listed by the user as moving.
- `data_train:` gets `features_type`, `features_use_channels_range`, `features_sub_length`, `features_sub_begin_random`, `features_sub_begin_sequence` (commented), `features_sub_step` (commented), `features_additive_noise_std`, `num_features` (commented), `targets_type`, `Ntrain`, `Nvalidate`, `train_shuffle_buffer_size`, `train_batch_size`.
- `data_evaluate:` gets the same feature/target duplicate set plus `Ntest`, `eval_batch_size`.

This affects `pytorch/data.py` (all the functions that read `params["data"][...]`) and `pytorch/run_dnn.py` (runtime-statistics logging that reads `Ntrain`/`Ntest`/batch sizes). `run_ae.py`/`run_unet.py` already reference a `data.py` API that doesn't match the current one (mismatched `load_data` return arity, calls to `preprocess_features_noise` which no longer exists) — they are pre-existing breakage, confirmed out of scope for this refactor.

`create_dataloader` in `data.py` already branches on `mode` (`Mode.TRAIN | Mode.PROFILE` vs `Mode.VALIDATE | Mode.PREDICT | Mode.EVAL`) to pick `train_batch_size` vs `eval_batch_size`, and it force-disables `features_sub_begin_random` in eval mode. This existing branch is the natural place to also source the other duplicated feature-preprocessing knobs per-mode.

`_load_and_split_arrays`/`load_data`, by contrast, load the full train+validate+test pool in a single call and are not mode-specific, so they need one merged view rather than a per-mode selection.

The toolkit's parameter override merger (`dlk/mgmt/parameters.py:_update_existing_nested_parameters`) only updates keys that already exist at the given path and otherwise just prints a warning and silently skips the override. This means `train_m4.sh`/`train_m16.sh`/`train_m64.sh`/`train_m256.sh`, which pass `--json_params '{"data": {"Ntrain": ..., "train_batch_size": ...}}'`, would silently stop overriding anything once these keys move — they must be updated to target `data_train`.

Eight other active config files under `pytorch/configs/` (`params_dnn_data2025.yaml`, `params_dnn_sg2026.yaml`, `params_dnn_hham.yaml`, `params_dnn_lorenz63.yaml`, `params_dnn_aidan-memmap-data.yaml`, `params_m4.yaml`, `params_m16.yaml`, `params_m64.yaml`, `params_m256.yaml`) use the same flat `data:` schema and are loaded directly by `run_dnn.py`; all must be migrated in lockstep with the code change or they will `KeyError` at runtime.

The repository has no existing pytest suite covering `data.py`/`run_dnn.py`. Verification will use a real smoke run (a few epochs of train+eval against the local `../data/2020-12-09` dataset) comparing key logged values before and after the refactor, instead of new regression tests.

### Settled design decisions

- Migrate all 9 active `params_dnn*.yaml`/`params_m*.yaml` files.
- Exclude `run_ae.py`, `run_unet.py`, `params_ae.yaml`, `params_unet.yaml` — pre-existing breakage, not touched.
- Update the `--json_params` key from `data` to `data_train` in all four `train_m*.sh` scripts.
- For merged (non-mode-specific) reads of duplicated keys, `data_train`'s copy wins over `data_evaluate`'s on conflict.
- Verification is a fast smoke run (3 epochs), not new pytest regression tests.

### Core principle

Introduce one small resolution helper in `data.py` that every existing call site funnels through, so the rest of each function's logic is untouched: `_resolve_data_params(params, scope)` returns a merged flat dict, where `scope` is `"train"` (`{**data, **data_train}`), `"evaluate"` (`{**data, **data_evaluate}`), or `"all"` (`{**data, **data_evaluate, **data_train}`, so `data_train` wins ties).

Call sites that already take a plain `data_params`-shaped dict (`_load_and_split_arrays`) need zero internal changes — only their caller changes what it passes in. Call sites that index `params["data"][...]` inline get a one-line resolved dict added at the top and their key accesses redirected to it.

## Terminology

- **data / data_train / data_evaluate**: the three top-level YAML sections after the split. `data` holds settings shared by every mode (paths, normalization flags, memmap sizes, derived shapes). `data_train` and `data_evaluate` each hold a full, self-contained copy of the feature/target preprocessing knobs plus their own sample-count and batch-size settings.
- **merged/resolved dict**: a plain `dict` built by `_resolve_data_params`, combining `data` with one or both of the new blocks, that downstream functions read from exactly as they used to read from `params["data"]`.
- **mode-specific vs. pool-wide**: `create_dataloader` is mode-specific — it is called once per `Mode` (train, eval, predict) and should see only that mode's `data_train`/`data_evaluate` values layered on `data`. `_load_and_split_arrays`/`load_data` are pool-wide — they load and slice the entire train+validate+test dataset in one pass and need both blocks merged together.

Pre-change line anchors (will shift once edits start; used only as search anchors):

- `data.py:344-420` `load_data(params, logger)`:

  - The logging lines reading `data_params['Ntrain']`/`['Nvalidate']`/`['Ntest']` (`data.py:411-413`) need no change since `data_params` is now the merged dict and still contains those unique keys.

- `data.py:423-432` `load_timesteps(params)` — no change; only reads `data_dir`, which stays in `data`.

- `data.py:476-545` `preprocess_features(...)` — add `data_params = _resolve_data_params(params, "all")` near the top; change `features_type = params["data"]["features_type"]` (`data.py:480`) to read from `data_params`; leave `params["data"].get("features_normalize", False)` (`data.py:496`) unchanged since it did not move.

- `data.py:566-593` `preprocess_targets(...)` — no change; it only reads `targets_normalize`, which stays in `data`.

- `data.py:619-678` `get_conditional_positions(features, params)` — resolve `features_type` the same way as above; `data_dir` access (`data.py:621`) stays unchanged.

- `data.py:714-742` `get_conditional_samples(...)` — same `features_type` resolution change.

- `data.py:943-1039` `create_dataloader(params, logger, mode, ...)` — the key change. Near the top (`data.py:956-961`), replace the five `params["data"].get(...)` reads (`features_additive_noise_std`, `features_sub_length`, `features_sub_begin_random`, `features_sub_begin_sequence`, `features_sub_step`) with reads from a mode-selected dict: `mode_scope = "train" if mode.any(Mode.TRAIN | Mode.PROFILE) else "evaluate"` and `mode_data_params = _resolve_data_params(params, mode_scope)`, then read all five plus `train_batch_size`/`eval_batch_size` (`data.py:965`, `data.py:968`) from `mode_data_params` instead of `params["data"]`. This requires reordering slightly so the `mode.any(...)` check happens before the five `.get(...)` calls; the existing `if/elif/else` branch structure for `shuffle`/`batch_size` (`data.py:963-977`) stays otherwise identical, just sourcing from `mode_data_params` instead of `params["data"]`.

Add the new helper near the top of `data.py` (after the existing `dictarray_*` helpers, `data.py:39`):

```python
def _resolve_data_params(params, scope):
    """Merge the shared `data` block with the train/evaluate-specific blocks.

    Args:
        params (dict): full parameter tree with `data`, `data_train`, `data_evaluate`.
        scope (str): one of "train", "evaluate", "all". "all" merges both
            mode-specific blocks on top of `data`, with `data_train` winning
            over `data_evaluate` on any conflicting key.

    Returns:
        dict: flat dict combining the relevant blocks.
    """
    if scope == "train":
        return {**params["data"], **params["data_train"]}
    elif scope == "evaluate":
        return {**params["data"], **params["data_evaluate"]}
    elif scope == "all":
        return {**params["data"], **params["data_evaluate"], **params["data_train"]}
    else:
        raise ValueError(f"Unknown scope: {scope}")
```

## 3. Config file migration

Apply the same split to all 9 active config files (`params_dnn.yaml` plus the 8 listed in Context). For each file:

- Keep `data:` with only the non-moved keys (in the order they currently appear).

- Add `data_train:` with `features_type`, `features_use_channels_range` (if present), `features_sub_length`, `features_sub_begin_random`, any commented `features_sub_begin_sequence`/`features_sub_step` lines, `features_additive_noise_std`, any commented `features_fft`/`num_features` lines, `targets_type`, `Ntrain`, `Nvalidate`, `train_shuffle_buffer_size`, `train_batch_size`.


- Add `data_evaluate:` with the same duplicated feature/target keys plus `Ntest`, `eval_batch_size`.

- Move only the lines existing in `data:`, do not add any lines that did not exist before.

- Preserve each file's actual values and its existing comments verbatim; only the section a key lives under changes. Files with extra keys not present in the base `params_dnn.yaml` (e.g. `file_names` in `params_dnn_sg2026.yaml`/`params_dnn_hham.yaml`/`params_dnn_lorenz63.yaml`, `features_cols_num`/`targets_cols_num` in `params_dnn_hham.yaml`, `features_use_length_range` in `params_dnn_lorenz63.yaml`, `autoencoder_load_dir`/`autoencoder_latent_size`/`features_sub_step` in `params_dnn_aidan-memmap-data.yaml`) keep those extra keys in `data` since none of them are in the user's moved-keys list.

- `params_dnn_aidan-memmap-data.yaml` uses 2-space indentation for `data:` and 4-space for `net:`; use a consistent 4-space indentation style for the new `data_train:`/`data_evaluate:` blocks.

## Risks / edge cases

- If a config file lets `data_train`/`data_evaluate` copies of a duplicated key drift apart, `_load_and_split_arrays`/`load_data`'s pool-wide behavior will silently follow `data_train`'s value (per the agreed precedence) while `create_dataloader`'s eval-mode dataloader will follow `data_evaluate`'s value — this is expected but worth a one-line comment in `data.py` next to `_resolve_data_params`.

- `config_params.save(...)` (`run_dnn.py:530`) serializes the full `params` dict for reproducibility; after the split, saved `params.yaml`/`params.json` in `runs/` will have the new three-way shape — this is expected but changes the shape of historical run artifacts going forward.
